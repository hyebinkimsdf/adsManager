# AI 역할 분리와 성능 최적화, 지금까지의 여정

이 프로젝트를 만들면서 겪은 문제들을 세 갈래로 나눠 정리했어요.

1. **AI는 판단하지 않고, 설명만 하게** — 광고 성과 판단을 코드로 옮기고, AI 호출 자체를 줄인 이야기
2. **브라우저 AI, 더 빠르게 준비되게** — 온디바이스 AI가 뜸 들이던 이유를 찾고 고친 이야기
3. **캠페인 수천 건에도 화면은 가볍게** — 데이터가 늘어나도 안 느려지게 만든 이야기

각 항목은 원인 → 시도한 내용 → 결과 순서로 적었어요.

---

## 트랙 1. AI는 판단하지 않고, 설명만 하게

### 1-1. "몇 %를 줄일지"까지 AI가 정하고 있었어요

**원인**

이번 주 추천 액션 카드를 만들 때, 실제로 예산을 바꾸는 순간(적용하기 클릭)은 이미 코드가
1~30% 범위로 제한하고 안전하게 처리하고 있었어요. 그런데 그보다 앞서 "어떤 캠페인을,
어떤 방식으로, 몇 %나 조정할지"를 추천하는 판단 자체는 여전히 AI가 자유롭게 고르고
있었어요. 그러다 보니 실행은 안전해도, 같은 데이터를 넣어도 추천 자체가 매번 조금씩
달라질 수 있다는 문제가 남아 있었어요.

**시도한 내용**

숫자로 판단할 수 있는 부분은 전부 코드가 맡도록 역할을 나눴어요.

- 캠페인 판단 로직을 "결정"과 "문구 생성" 두 단계로 쪼갰어요. 결정 단계는 ROAS·트렌드
  기준으로 어떤 캠페인을 어떤 종류로 몇 % 조정할지, 그 근거 수치까지 정하고 문구는
  만들지 않아요.
- AI에게는 이미 정해진 결정(캠페인, 조정 종류, 퍼센트, 근거 수치)만 전달하고,
  `{campaignId, title, detail}`처럼 사람이 읽을 제목 한 줄과 설명 한 줄만 써 달라고
  요청 범위를 좁혔어요. 프롬프트에도 "이 결정을 바꾸지 말라"고 명시했어요.
- AI가 특정 캠페인을 빼먹거나 이상한 값을 주면, 그 항목만 조용히 미리 준비한 문구로
  대체하도록 했어요. AI가 하나도 응답하지 못해도 기존 템플릿 문구가 그대로 나가도록
  완전 오프라인 폴백을 남겨뒀어요.
- 이미 화면에서 안 쓰이던 "캠페인 한눈에 보기" AI 응답 필드(spotlights)도 이 김에
  같이 걷어냈어요. 안 쓰는 AI 계약을 유지보수하는 건 손해라고 판단했어요.

**결과**

- 어떤 광고를, 어떤 방식으로, 얼마나 조정할지는 항상 코드가 정하고, AI는 그 내용을
  쉬운 말로 옮기는 역할만 하게 됐어요.
- 같은 데이터에서는 항상 같은 판단이 나오고, AI는 표현만 자연스럽게 다듬어요.
- AI가 실패해도 추천 기능 자체는 그대로 동작해요.
- 타입 체크·린트·테스트 55개 통과, Playwright로 홈 화면을 직접 열어 추천 카드가
  실제 캠페인명·퍼센트·근거 수치로 정상 렌더링되는 것까지 확인했어요.

핵심을 한 줄로 말하면: 기존엔 AI에게 "뭘 해야 할지 생각해줘"라고 했다면, 이제는 코드가
"뭘 해야 할지" 정하고 AI에게는 "이걸 쉽게 설명해줘"라고만 부탁하는 구조예요.

### 1-2. 안 바뀌어도 되는 문장까지 AI와 번역을 거치고 있었어요

**원인**

1-1로 판단은 코드가 하게 됐지만, 화면에 보여줄 문장은 여전히 AI가 새로 쓰고 있었어요.
게다가 브라우저 온디바이스 모델이 한국어를 공식 지원하지 않아서, 모델은 영어로 돌리고
번역기로 영→한 왕복 번역까지 거치고 있었어요. 필요하지 않은 부분까지 AI와 번역을
거치다 보니 응답이 느려지고, 같은 상황에서도 표현이 매번 달라지거나 광고 이름·숫자
같은 값이 번역 과정에서 미묘하게 바뀔 위험이 있었어요.

**다른 방향도 검토했어요**

- AI가 만든 문장은 그대로 두고 프롬프트를 더 강하게 제한하는 방법
- 번역 전에 광고 이름·숫자를 임시 토큰으로 바꿔뒀다가, 번역 후 원래 값으로 되돌리는 방법

**선택하지 않은 이유**

두 방법 다 번역 중 값이 바뀌는 문제는 줄여주지만, "코드가 이미 답을 알고 있는 부분까지
AI와 번역을 계속 거쳐야 한다"는 구조 자체는 그대로였어요. 주간 광고 분석처럼 경우의 수가
정해져 있고 필요한 숫자도 이미 코드가 계산해 둔 곳에서는, 단지 문장을 다양하게 만들기
위해 AI 호출과 왕복 번역을 유지하는 게 얻는 것보다 비용이 더 크다고 판단했어요.

**시도한 내용**

- 주간 광고 분석은 AI 호출 없이 코드가 직접 문장을 만들도록 바꿨어요. (`lib/insights.ts`의
  `decideWeeklyRecommendations`가 판단과 함께 title/detail 문장까지 그 자리에서 완성해요.)
- 캠페인 설정 화면의 버튼 문구도 정해진 값에 따라 코드에서 만들도록 했어요.
- 사용자가 자유롭게 묻는 채팅처럼, 진짜 자유 발화가 필요한 곳에서만 AI와 번역을 쓰도록
  범위를 좁혔어요.
- 채팅에 남겨둔 AI+번역 경로에서는, 광고 이름처럼 바뀌면 안 되는 값을 숫자 토큰(`#12345`
  같은 참조)으로 바꿔 모델에 보내고, 응답이 돌아오면 코드가 다시 실제 이름으로 채워
  넣도록 별도로 보호했어요. 모델이 이름을 직접 보지 않으니 "시드 캠페인"이 번역을 거치며
  "씨앗 캠페인"으로 둔갑하는 일이 원천적으로 사라져요.

**결과**

- 불필요한 AI 호출과 번역 왕복을 없앴어요.
- 같은 상황에서는 항상 같은 안내를 보여주고, 광고 이름·숫자가 번역 과정에서 달라질
  위험도 사라졌어요.
- AI가 없어도 주간 분석·캠페인 설정 같은 핵심 기능은 그대로 동작하고, 정말 자유로운
  설명이 필요한 채팅에서만 AI를 쓰게 됐어요.

AI를 더 많이 쓰는 대신, 꼭 필요한 곳에만 쓰도록 바꾼 거예요.

## 트랙 2. 브라우저 AI, 더 빠르게 준비되게

### 2-1. 셋 다 끝나야 뭐든 "사용 가능"이라고 뜨던 문제

**원인**

대화·캠페인 초안·추적 규칙, AI 세션 3개와 번역기 2개가 전부 끝나야 뭐든 "사용 가능"으로
표시되는 구조였어요. 대화만 필요한 사용자도 가장 느린 자원(추적 규칙 AI, 3.32초)까지
기다려야 했어요.

**시도한 내용**

1. 기능별 준비 상태를 분리했어요 — 대화 사용 가능 = 대화 세션 + 번역기 2개만 확인,
   다른 기능 상태가 대화를 막지 않도록 했어요.
2. 준비 순서에 우선순위를 뒀어요 — 대화·번역기를 먼저 준비하고, 캠페인 초안·추적 규칙은
   백그라운드에서 순서대로 준비하도록 했어요.
3. 세션 수명을 분리했어요 — 캠페인 초안·추적 규칙은 요청마다 기본 세션을 복제해서 쓰고
   끝나면 해제해요(대화만 문맥을 계속 유지해요).
4. 요청별로 대기를 취소·제한했어요 — 준비 대기는 15초로 제한하고, 요청이 끝나면 그
   요청의 대기도 함께 취소돼요.

**결과**

- 캠페인 초안(2.70s → 1.10s), 추적 규칙(3.32s → 0.90s)이 실제로 빨라졌어요. 세션 3개가
  더 이상 서로 자원을 두고 경쟁하지 않게 된 효과예요.
- 그런데 대화 AI 세션 "생성"(페이지 진입 시 미리 세션을 만들어두는 단계)만 2.08s에서
  22.47s로 한 번 튀는 걸 발견했어요. 채팅 응답 속도가 아니라 진입 시 예열 단계의
  시간이라, 실제 대화와는 무관하지만 경쟁 상대가 줄었는데 느려진 거라 코드 로직
  문제로 보긴 어려웠고, 이번 실행의 이상치일 가능성이 크다고 보고 반복 측정으로
  재현 여부를 확인하기로 했어요.
- 재측정(run:2) 결과, 22.47초는 다시 나타나지 않았고 오히려 전 구간이 더 빨라졌어요.
  한국어→영어 258ms, 영어→한국어 293ms, 대화 AI 사용 가능 1.40초(33% 단축), 캠페인
  초안 자체 생성 491ms(82% 단축), 추적 규칙 자체 생성 599ms(82% 단축), 전체 준비 완료
  2.50초(25% 단축)로 확인했어요. 지난번 22초는 그 실행 한 번의 이상치였던 걸로
  결론지었어요.

### 2-2. "대화가 준비돼야만" 나머지가 백그라운드로 깨어나던 문제

**원인**

코드를 다시 들여다보니, 백그라운드 예열을 시작하는 조건이 "대화 AI 자신이 available인가"
하나뿐이었어요. 캠페인 초안을 먼저, 성공적으로 써도 대화 AI를 한 번도 연 적이 없으면
나머지 기능은 백그라운드에서 영원히 예열되지 않는 구조였어요. 캠페인 초안 화면으로 바로
들어와서 대화창을 한 번도 안 연 사용자라면, 나중에 추적 규칙을 처음 쓸 때마다 매번
콜드 스타트를 겪게 되는 셈이었어요.

**시도한 내용**

- 백그라운드로 나머지를 깨우는 조건을 "대화가 준비됐는가"에서 "**방금 어떤 기능이든
  자신의 의존성까지 모두 준비됐는가**"로 일반화했어요. 깨울 대상도 "대화를 제외한
  나머지"가 아니라 "**방금 준비된 기능을 제외한 나머지**"로 바꿨어요.
- 셋 중 아무거나 하나만 먼저 준비돼도, 나머지 두 개가 자동으로 뒤따라 준비되도록
  했어요. 어떤 기능을 먼저 쓰든 상관없어졌어요.
- 브라우저 정책상 AI를 처음 켜려면 화면을 한 번은 눌러야 다운로드가 시작돼요. 지금까진
  "AI 사용 시작" 버튼을 직접 찾아 눌러야만 이 조건이 채워졌는데, 이제는 화면 아무
  데나 첫 클릭·키 입력만 해도 조용히 다운로드를 재시도하도록 했어요. 버튼을 못 찾아서
  AI가 안 켜지는 일을 줄였어요.

**결과**

타입 체크·린트·테스트 77개(신규 2개 포함)·빌드까지 전부 통과했어요. 다만 실제 크롬에서
"방금 클릭했다"는 신호가 이 정도 지연 뒤에도 살아 있는지는 브라우저가 없는 개발
환경이라 직접 확인하지 못했고, 실제 크롬에서 콘솔 로그로 확인이 필요하다고 남겨뒀어요.

### 2-3. 방문하지도 않은 화면의 AI까지 미리 준비하던 문제

**원인**

2-1, 2-2로 셋이 서로 덜 기다리게는 됐지만, 여전히 사이트에 들어오기만 하면 세 기능을
전부 백그라운드에서 준비하고 있었어요. 채팅에 필요한 준비가 끝나도, 다른 AI 도구가
모두 준비될 때까지 채팅 사용 가능 표시가 늦어지는 문제도 남아 있었어요 — 대화 AI가
2.09초에 준비돼도, 추적 규칙 AI가 끝나는 3.33초가 돼서야 채팅을 쓸 수 있었어요.

**시도한 내용**

필요한 기능을, 필요한 시점에만 준비하도록 바꿨어요.

- 사이트 진입: 대화 AI와 번역기 두 개만 준비해요.
- 캠페인 생성 화면 진입: 캠페인 초안 AI를 그때 준비해요.
- 추적 설정 화면 진입: 추적 규칙 AI를 그때 준비해요.
- 같은 화면 재방문: 이미 준비한 기본 세션을 재사용해요.
- 일회성 작업 완료: 작업에 쓴 복제 세션을 해제해요.

번역기는 여러 기능이 함께 쓰고, 한 기능의 준비가 실패해도 이미 준비된 다른 기능은
계속 쓸 수 있어요.

**결과**

기능별 준비 분리 직후 측정에서는 채팅이 약 2.55초부터 사용 가능해졌어요(이전 3.33초
대비 0.78초 단축). 이후 화면별 온디맨드 방식으로 한 번 더 바꾸면서, 지금은 방문하지
않은 화면의 세션을 아예 만들지 않아요. 타입 체크·변경 파일 린트·빌드·테스트 84개가
통과했고, 런타임 테스트 29개로 홈에서 세 자원만 생성되는지, 화면별 생성·재사용이
되는지, 화면 이탈 시 불필요한 사전 준비를 건너뛰는지, 공유 번역기만 실패했을 때
재시도가 되는지까지 확인했어요. 다만 실제 크롬에서의 체감 속도는 이 환경에 브라우저가
없어 아직 측정하지 못했어요.

### 2-4. 대화가 길어질수록 캠페인 정보를 매번 처음부터 다시 보내던 문제

**원인**

채팅으로 대화를 이어갈수록, 데이터가 하나도 안 바뀌었는데도 AI에게 캠페인 정보 전체를
매번 다시 알려주고 있었어요. 대화가 길어질수록 AI가 처리할 양이 계속 쌓였고, 어느
순간 12초 안에 답을 끝내지 못해 타임아웃이 나면서 준비된 기본 답변이 대신 나가는
상황까지 생겼어요.

**시도한 내용**

캠페인 정보를 매번 다시 보내는 대신, 두 경우에만 다시 보내도록 바꿨어요.

1. 실제로 데이터가 바뀌었을 때 — 예를 들어 대화 중에 예산을 실제로 조정했을 때
2. 안 바뀌었어도 마지막으로 보낸 지 몇 턴이 지났을 때 — 작은 모델이라 오래 기억하지
   못할 수 있으니, 가끔 한 번씩 다시 알려주는 안전장치예요

이 두 경우가 아니면 생략하고, AI가 이미 아는 내용을 그대로 기억하게 뒀어요. "마지막으로
언제 보냈는지"는 채팅창이 아니라 실제로 대화를 기억하는 쪽(온디바이스 세션의 런타임
상태)에 저장해서, 채팅창을 껐다 켜도 정확히 기억하도록 했어요. 몇 턴에 한 번씩 다시
보낼지는 4~5턴으로 시작했어요.

**결과**

`lib/ai/onDeviceAiRuntime.ts`에 모델별 `contextSignature`/`turnsSinceContext`를 두고,
서명이 바뀌었거나 기준 턴 수를 넘겼을 때만 전체 컨텍스트를 다시 보내도록 구현했어요.
실제 크롬에서의 정확한 체감 개선치와 최적 턴 수는 앞으로 테스트하면서 맞춰갈 예정이에요.

## 트랙 3. 캠페인 수천 건에도 화면은 가볍게

### 3-1. 캠페인이 늘어날수록 홈 화면이 통째로 무거워지던 문제

**원인**

"가상의 대량 데이터를 넣고 API가 어떻게 처리되는지 보고 싶다"는 요청으로 조사해보니,
`GET /api/campaigns`가 페이지네이션 없이 전체를 반환하고 있었어요. 클라이언트는 그
전체 배열 하나를 캐싱해서 홈 대시보드와 AI 어시스턴트가 전부 거기서 파생 계산을 하는
구조라, 캠페인이 수천 건이 되면 캠페인마다 14일치 이력 JSON까지 포함한 응답을 매번
통째로 받아야 했어요.

**시도한 내용**

- 캠페인 2,000건을 실제 원격 D1에 시드로 넣었어요(바인딩 파라미터 제한 때문에 문장당
  20행씩 나눠 99개 INSERT로 처리).
- 홈 화면 계산 로직을 서버로 옮기고 `GET /api/campaigns/summary`를 새로 만들어, 홈이
  필요로 하는 요약값만 반환하도록 했어요.
- `GET /api/campaigns`에 `?limit&cursor` 방식의 옵션 페이지네이션을 추가했어요(파라미터
  없으면 기존처럼 전체 반환).
- AI 어시스턴트에는 최근 7일 지출 상위 20개만 추려서 넘기도록 해서, 캠페인이 몇 건이든
  AI 프롬프트 크기가 일정하게 유지되도록 했어요.

**결과**

캠페인이 8건에서 2,008건(250배)으로 늘어도, `campaigns/summary` 응답은 13.4KB에서
38KB로만 늘었어요(`campaigns` 전체 조회는 9.4KB → 3.3MB로 그대로 커졌지만, 홈 화면은
더 이상 이걸 쓰지 않아요). 타입 체크·린트·테스트 55개 통과.

### 3-2. "목록 보기"를 눌러도 화면이 안 나오던 문제

**원인**

"캠페인 목록 보기를 누르면 내용이 나와야 한다"는 버그 리포트를 받았어요. Playwright로
재현해보니 콘솔 에러도, API 에러도 없었어요 — 캠페인 2,008건을 필터 없이 전부
`CampaignListItem`으로 렌더링하느라 화면에 나타나기까지 렌더링에만 수 초가 걸리고
있었어요. 느린 게 "안 나오는 것"처럼 보였던 거예요.

**시도한 내용**

`visibleCount` 상태로 초기 30건만 렌더링하고, "더 보기" 버튼으로 30건씩 늘려가도록
바꿨어요. 필터를 바꾸면 `visibleCount`도 초기화돼요.

**결과**

렌더링된 본문 텍스트가 111,602자(2,008건 전부)에서 1,657자(30건)로 줄었고, 클릭 후
반응 시간은 1,076ms에서 209ms로 줄었어요. 타입 체크·린트·테스트 55개 통과.

### 3-3. 재방문할 때마다 같은 데이터를 다시 요청하던 문제

**원인**

홈 → 캠페인 → 홈 → 캠페인처럼 메뉴로 이동할 때, 요약 API 2회·목록 API 2회를
요청하고 있었어요. 캐시는 있었지만 `staleTime` 기본값이 0이라 재마운트할 때마다
다시 조회했어요. (전체 페이지를 매번 새로 여는 방식으로 측정하면 4회·2회가 나오는데,
이건 메모리 캐시 초기화와 공통 채팅 영역의 요약 조회가 겹친 별도 조건이라 메뉴
이동과는 구분해야 했어요.)

**시도한 내용**

- `["campaigns"]` 계열(목록·요약·상세)에만 `staleTime: 30_000`을 적용했어요. 다른
  API의 캐시 정책은 그대로 뒀어요.
- 데모 데이터로 미리 채워두던 `placeholderData`를 실제 응답 캐시와 분리해서, 첫
  조회는 항상 바로 실행되도록 했어요.
- 캠페인을 변경하면 이전 목록·요약·해당 상세 캐시를 무효화하고 최신 값을 반영하도록
  했어요. 단건 변경 때문에 다른 캠페인들의 캐시 신선도가 덩달아 늘어나지 않도록
  기존 `dataUpdatedAt`은 보존했어요.

**결과**

같은 조건(D1 캠페인 2,008건, 메뉴 링크로 홈 → 캠페인 → 홈 → 캠페인 이동)에서 재측정한
결과, 요약 API가 2회 → 1회, 목록 API가 2회 → 1회로 줄었고 두 API 응답 본문 합계는
약 6.75MB에서 3.37MB로 절반이 됐어요. 두 번째 방문에서는 추가 요청이 0회였어요.

TTL이 실제로 갱신되는지도 확인했어요 — 31초 뒤 재방문하면 요약·목록을 다시
조회했고(615ms·600ms), 갱신 직후 바로 재방문하면 추가 요청 없이 캐시를 그대로
썼어요. 새로고침은 여전히 두 API를 다시 요청해요(이건 의도한 그대로예요).

다만 이건 "반복 조회를 줄인 것"이지 "첫 조회 자체를 빠르게 만든 것"은 아니에요. 목록·
요약 API가 D1 전체 행을 조회하는 구조 자체는 그대로 남아 있고, 그건 별도 최적화
대상으로 남겨뒀어요. 새 캐시 테스트 18개를 포함한 전체 102개 테스트, 타입 체크, 빌드
모두 통과했어요.

## 한 줄로 정리하면

- **AI 역할**: 광고를 어떻게 바꿀지는 코드가 정하고, AI는 그걸 쉬운 말로 옮기는
  역할만 해요. 정말 자유로운 설명이 필요한 채팅에서만 AI와 번역을 계속 써요.
- **온디바이스 AI 준비**: 안 쓰는 화면의 AI까지 미리 준비하지 않고, 필요한 화면에서
  필요한 것만 준비해요. 대화가 길어져도 안 바뀐 정보는 매번 다시 안 보내요.
- **대량 데이터**: 화면에 필요한 만큼만 서버에서 계산해서 보내고, 재방문했을 때는
  신선한 캐시를 그대로 재사용해요.

측정 없이 "빨라졌을 것 같다"고 말하지 않고, 매번 같은 조건에서 다시 재보면서 이상치인지
실제 개선인지를 가려낸 것도 이 과정에서 계속 지킨 원칙이에요.
