# 브라우저 AI 준비 Provider

## 동작

- `app/layout.tsx`의 `OnDeviceAiProvider`가 브라우저 AI 실행 객체를 소유한다.
- 진입 시 영어 모델과 한국어↔영어 언어쌍 지원 상태를 확인하고, 대화 AI와 번역기 두 개를 우선 준비한다. 이미 설치된 경우에도 `create()`를 호출해 실행 세션을 미리 준비한다.
- 사이트 진입 시 대화 AI와 번역기만 생성한다. 캠페인 초안은 `/campaigns/new`, 추적 규칙은 `/tracking` 화면 진입 시 추가로 준비한다. 특정 화면으로 바로 들어와도 그 기능은 대화 준비 완료를 기다리지 않는다. 다른 기능으로 준비를 전파하는 백그라운드 예열은 하지 않는다.
- 번역기 두 개는 모든 기능이 공유한다. AI 세션은 대화·캠페인 초안·추적 규칙의 시스템 프롬프트별로 분리한다. 각 기능의 사용 가능 상태는 해당 AI 세션과 공유 번역기 두 개로 판단한다. 다른 기능의 세션 생성 실패는 이미 준비된 기능을 막지 않는다.
- 사용자 활성화가 필요해 자동 생성이 거절되면 `AI 사용 시작` 버튼을 표시한다. 페이지의 클릭·키 입력으로도 대화와 현재 화면의 기능만 재시도한다. 모델은 준비됐지만 공유 번역기만 거절된 경우도 재시도한다. 방문하지 않은 기능을 깨우지는 않는다.
- 진행 중인 준비 요청은 중복 생성하지 않는다. 일부 자원만 실패했다면 이미 성공한 자원을 재사용하고 실패한 자원만 재시도한다.
- 준비 대기 / 확인 중 / 시작 필요 / 다운로드 중 / 실행 준비 중 / 사용 가능 / 실패를 구분한다. 다운로드 100%와 세션 생성 완료는 별개다.
- 기본 배너 상태는 대화 AI 기준이다. 캠페인 초안·추적 규칙의 상태와 시작·재시도 버튼은 해당 화면에서만 표시한다. 사용하지 않는 기능의 준비 대기 문구는 표시하지 않는다.
- 상세 배너에서는 다운로드 중인 각 자원의 진행률을 따로 표시한다. `downloadProgress`는 해당 기능에 필요한 자원의 준비 진행률 평균이며 다운로드 바이트 비율이 아니다.
- 대화 세션은 문맥을 유지한다. 캠페인 초안·추적 규칙은 실제 요청을 보내지 않는 기본 세션을 복제해 요청마다 독립적으로 실행하고 완료 후 복제본을 해제한다. 복제 API를 지원하지 않으면 같은 초기 프롬프트로 새 세션을 생성한다.
- 개별 요청의 기능 준비 대기와 세션 복제 대기는 각각 15초로 제한한다. 이 대기의 취소·시간 초과가 공유 자원의 생성을 취소하지 않으므로 이미 시작한 준비는 계속된다. 준비 완료 후 번역·추론의 기존 9~12초 제한 시간을 시작한다.
- 개별 요청을 취소해도 Provider가 소유하는 공용 세션을 해제하지 않는다.
- 페이지 이동으로 개별 훅이 해제돼도 공유 자원은 유지한다. Provider 해제 시 준비를 취소하고 실행 자원을 해제한다. 해제 뒤 늦게 도착한 생성 결과도 폐기한다.
- 이미 방문한 화면의 기본 세션은 재방문 시 재사용한다. 초기 지원 확인 도중 화면을 나가면 아직 시작하지 않은 해당 화면의 사전 준비는 건너뛴다. 요청별 복제본은 기존처럼 완료 후 해제한다.

## 저장 범위

Provider는 현재 페이지 수명의 실행 객체를 공유한다. 전체 새로고침에서는 세션을 다시 생성한다. 모델 파일 저장은 Chrome이 관리하며 이 구현은 모델을 Web Storage나 서버에 저장하지 않는다.

Chrome API의 사용자 활성화 및 세션 수명 계약은 [Prompt API](https://developer.chrome.com/docs/ai/prompt-api), [Translator create](https://developer.mozilla.org/en-US/docs/Web/API/Translator/create_static)를 참고한다.

## 확인

브라우저 개발자 도구 Console에서 `on-device-ai`로 필터링하면 Provider 시작·종료, API 지원 여부, 원본 availability, 대화 기준 준비 상태와 각 기능의 상태 전환, 자원별 준비 시간, 세션 재사용 및 재시도를 확인할 수 있다. `Info` 로그 수준을 켜야 한다. 진행 이벤트는 10% 구간마다 기록하고, 다운로드 100%와 실제 세션 생성 완료를 별도로 기록한다. `run`은 같은 Provider의 수명 시작 횟수이며 `elapsedMs`는 해당 시작 이후 경과 시간이다. 프롬프트나 번역 내용은 준비 로그에 포함하지 않는다.

2026-09-12 화면별 준비 변경 후 타입 검사(`tsc --noEmit`), 변경 파일 ESLint, 전체 테스트(`npm test`, 84개), 프로덕션 빌드(`npm run build`)가 통과했다. 런타임 테스트 29개에는 홈에서 세 자원만 생성, 화면별 생성·재사용, 화면 이탈 후 사전 준비 제외, 공유 번역기만 실패한 경우의 활성화 재시도가 포함된다. 실제 Chrome의 모델 다운로드·추론 속도는 이 환경에서 검증하지 않았다.

`useOnDeviceAi.ts`가 실제로 `waitForFeature`·`createTaskSession`/`releaseTaskSession`을 호출하도록 연결하기 전까지는, 이 문서가 설명하는 기능별 준비·세션 복제 동작이 Runtime에만 구현되어 있고 세 기능(채팅·캠페인 초안·추적 규칙) 어디서도 실제로 쓰이지 않았다. 캠페인 초안·추적 규칙 요청은 대화 기능(우선 준비 대상)의 준비만 기다린 뒤, 아직 준비되지 않았을 수 있는 자기 모델의 세션을 곧바로 조회해 실패하기 쉬웠고, 준비된 뒤에도 요청마다 복제 없이 Provider의 공용 세션을 직접 사용해 이전 요청의 문맥이 남을 수 있었다. `useOnDeviceAi.ts`를 연결하며 함께 발견한 `createTaskSession`의 늦게 도착한 clone 정리 로직은 별도의 promise 체인이라 호출자의 대기가 끝난 뒤 한 틱 늦게 끝날 수 있어(실제 유실은 아님), 테스트의 확인 시점만 한 틱 늦췄다(`tests/on-device-ai-runtime.test.cjs`).
